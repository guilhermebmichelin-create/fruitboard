## G3 proposal: cross-check cloned Sampler labels in FL Studio 2025

Read-only availability verification on 2026-10-14 found executable files with
both file and product versions `25.1.3.4922` and `26.1.0.5530`, matching the two
registered Windows application versions. Neither application was launched for
this proposal. File/registry metadata does not prove that the matching GUI can
start or create the proposed case; verify the actual About/build display before
authoring. The private receipt contains the host-specific details.

Use provisional **F22** for one new compatibility case in exact build `25.1.3.4922`, if that executable is available and the owner approves operation. F15 shows that cloning empty Samplers in `26.1.0.5530` can produce repeated visible `Sampler` labels; F06 covers only one Sampler in `25.1.3.4922`. F22 would check whether the existing 2025 inference is justified for a multi-channel clone case. This would add a case within an already represented build, not a new version row.

Before opening the parser or inspecting event bytes, register the recipe and the GUI observation sheet. Start from an independent copy of approved F06 in its matching build, keep 130 BPM, and clone the empty built-in Sampler until there are three channels. Do not rename them. In FL Studio, record the exact visible label and generator for each channel, its File field, total channel count, and the absence/presence of notes, Playlist clips, samples, and other added content. The hypothesis under test is three visible `Sampler` labels; treat that as a hypothesis until the matching GUI confirms it. Reopen the sanitized candidate in the same build without saving, capture private screenshots of the labels and empty fields before extraction, and confirm the bytes remain unchanged.

If the GUI shows a different label pattern, preserve that exact observation and reassess the candidate's value before any parsing. Do not edit saved labels after looking at bytes to make the fixture fit the parser. Register the visible label array as the GUI oracle before extraction. Then independently record whether each label was stored or inferred from the event stream: if all three visible labels are `Sampler` and no label is stored, the expected inferred values are `Sampler`, with the existing high/medium/medium per-item confidence; if labels are stored, expected parser status is extracted with their exact saved text. If the GUI values and bytes cannot support either result, keep the field unavailable/unsupported and add no broader inference.

The focused code boundary is `known_sampler_default_build` and `channel_names_json` in [`crates/flp-parser/src/lib.rs`](../../../crates/flp-parser/src/lib.rs), with regression coverage in [`crates/flp-parser/tests/generators.rs`](../../../crates/flp-parser/tests/generators.rs), [`crates/flp-parser/tests/corpus.rs`](../../../crates/flp-parser/tests/corpus.rs), and [`crates/flp-parser/tests/validation.rs`](../../../crates/flp-parser/tests/validation.rs). Keep `channelGeneratorNames` unsupported in 2025; F22 would not qualify generator-name extraction. F06 is the genuine one-channel control. Constructed mixed-name, wrong-build, channel-count mismatch, and malformed-reply cases can exercise refusal paths, but remain constructed.

If the exact GUI and parser observations agree, a later fixture PR can add the approved sanitized candidate and registered expectations to the manifest, allowlist only its named path and exact SHA-256 in [`scripts/lib/repository-privacy.mjs`](../../../scripts/lib/repository-privacy.mjs), and pin the same bytes/GUI values in [`tests/repository-privacy.test.mjs`](../../../tests/repository-privacy.test.mjs) and corpus tests. The manifest and tests must keep GUI expectations separate from parser output. The owner must approve the exact candidate bytes and expectations for public inclusion after privacy review. Until then, add no manifest row, support claim, or hash.

## G6 proposal: count saved automation clips and their visible control points

Use provisional **F23** for a single controlled automation case in exact build `26.1.0.5530`, subject to current executable availability and owner approval. Report only the saved automation-clip count and saved control-point count for the qualified one-clip layout. Do not report the target parameter, evaluate a curve, estimate rendered duration, claim playback behavior, or interpret MIDI. This gives the Library one bounded automation summary while keeping the saved-record facts separate from what a project may sound like.

Use an independent copy of approved F11: 130 BPM, one empty built-in Sampler, no notes or sample reference. Through the matching GUI, create exactly one automation clip linked to that Sampler's volume and place it from bar 1 to bar 2. Make exactly three visible control points (clip start, middle, and end), then record the target, positions, displayed values, Playlist lane, and clip boundaries in a private preregistration and screenshot set before reading bytes. These are intended case facts, not observations yet. Reopen the sanitized candidate without saving or playback; independently confirm and capture the same visible facts before parser extraction. If the UI cannot demonstrate exactly three points or the case cannot be reopened unchanged, reject the candidate rather than infer the count.

F11's empty Playlist/event-233 payload is the existing genuine no-clip control. Do not infer automation framing from F16/F17: their 24-byte records are independently qualified note records, and automation may use a different layout or opaque state. The parser currently accepts only a narrow pattern-clip interpretation of event 233; a new summary must not weaken that behavior. If the automation facts cannot be bounded from independently understood saved records, or require reading opaque plugin state, stop with an unsupported result and keep G6 open.

The prospective parser files are a new `crates/flp-parser/src/automation.rs`, event capture and response wiring in [`crates/flp-parser/src/lib.rs`](../../../crates/flp-parser/src/lib.rs), a new `crates/flp-parser/src/validation/automation.rs`, and corresponding descriptor/full-projection checks in [`crates/flp-parser/src/validation.rs`](../../../crates/flp-parser/src/validation.rs) and [`crates/flp-parser/src/validation/project_facts.rs`](../../../crates/flp-parser/src/validation/project_facts.rs). Limits must charge all candidate clips and points before selecting output, reject ambiguity/duplicates/unknown layouts, and never truncate a malformed or over-limit list into a successful summary.

If parser qualification succeeds and the owner accepts a Library summary, the later vertical slice should follow the existing immutable projection path: [`crates/storage-sqlite/src/metadata/payload.rs`](../../../crates/storage-sqlite/src/metadata/payload.rs) and [`crates/storage-sqlite/src/metadata/tests.rs`](../../../crates/storage-sqlite/src/metadata/tests.rs), native details projection in [`apps/desktop/src-tauri/src/foundation/project_details.rs`](../../../apps/desktop/src-tauri/src/foundation/project_details.rs), and the decoder/view in [`apps/client/src/library/projectDetails.ts`](../../../apps/client/src/library/projectDetails.ts), [`apps/client/src/library/ProjectDetailsPanel.tsx`](../../../apps/client/src/library/ProjectDetailsPanel.tsx), and their tests.
