## Defect register

### D1 — Installed native Library is labeled as a fake adapter

Reproduction:

1. Build and install the exact package recorded above with
   `packaging-smoke,scan-console`.
2. Launch it and open Library with a tracked root.
3. Observe the visible badge `Review harness · fake adapter` and inspect the
   Library root element, which reports
   `data-review-adapter="fake-or-proposed"`.
4. The installed desktop entry mounts the native adapter, so the label
   conflates installed native evidence with fake-adapter evidence.

Impact: an operator cannot tell from the installed product whether the
observed Library is native or a review harness. This directly violates the
evidence boundary required by the checklist. Application code was not changed
in this documentation run.

### D2 — Retry is offered after cancellation but the installed native command rejects it

Reproduction:

1. Add the cancellation fixture root and let its first scan commit rows.
2. Start `Scan now`, wait for the native `Running`/`Cancel` state, and click
   Cancel.
3. Wait for `Cancelled`, then click the enabled `Retry` control.

Observed result: the status stayed `Cancelled` and the UI message was
`The scan state changed. Refresh the status and try again.`. The UI still
offered Retry. The native retry path only accepts a Failed job; a Cancelled
job is rejected by [`scan_console.rs`](../../../../apps/desktop/src-tauri/src/foundation/scan_console.rs#L508).
Prior committed rows were retained, but the visible Retry action was not
actionable.

### D3 — Restored unavailable root did not provide an actionable Retry after automatic exhaustion

Reproduction:

1. Start from the primary root with committed rows.
2. Move the selected synthetic leaf away, let the native watcher report the
   unavailable-root failure and automatic retries, then restore the leaf.
3. Click Retry while the root is available again.

Observed result: the UI returned the same state-change message and did not
reconcile. The isolated DB showed the failed chain at attempt 4 of 4. The
checklist expectation says Retry can reconcile after access returns; a
successful explicit retry was therefore not verified. This may be an intended
durable-budget policy, but the installed UI gives no actionable path after the
budget is exhausted, so it remains an acceptance gap for owner disposition.
