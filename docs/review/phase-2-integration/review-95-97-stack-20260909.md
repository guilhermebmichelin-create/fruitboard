## Verdicts

### 1. `retryAvailable` agrees with native eligibility and durable budgets

Agreement holds across all three layers:

- Native status
  (`apps/desktop/src-tauri/src/foundation/scan_console.rs:706-708`)
  sets `retry_available` true only for `Failed` with
  `attempt < max_attempts` and an enabled root.
- Durable `retry_failed_scan_job`
  (`crates/storage-sqlite/src/execution.rs:1395-1414`) requeues only for
  `Failed` with `attempt < max_attempts` and an enabled root, returning
  `false` otherwise; the native `retry_scan` maps `false` to the safe
  `conflict` (`scan_console.rs:529-548`), and terminal
  `Cancelled | Interrupted | Completed` maps to `conflict`
  (`scan_console.rs:552-554`).
- The client parser (`apps/client/src/library/native.ts:277-286`)
  requires a boolean and rejects `retryAvailable=true` unless the status
  is `failed` with a non-null `jobId` and an enabled root. The client
  cannot check the attempt budget (no attempt field crosses the seam),
  so it correctly trusts the native flag instead of guessing.

Automated pins: eligible failed `retryAvailable=true`
(`scan_console/tests.rs:650`); disabled failed `false`
(`scan_console/tests.rs:1122`); completed `false`
(`scan_console/tests.rs:444`). The review follow-up (`c4754a2`) adds the
two previously unasserted renderer-visible flags the D2/D3 claims depend
on: cancelled `retryAvailable=false` (`scan_console/tests.rs:1210-1219`)
and exhausted (attempt 4/4) `retryAvailable=false` via
`list_scan_statuses` (`scan_console/tests.rs:1803-1812`). No
queued-state, cancellation-lease, or burst coverage was duplicated.

### 2. Scan now creates fresh work without resetting old chains

`enqueue_scan_tx` (`crates/storage-sqlite/src/execution.rs:725-806`)
creates a new job with a new `retry_chain_id` at attempt 0 when no
queued/running job exists (`:784-800`), and coalesces onto the active
slot otherwise. Native tests prove both post-terminal paths preserve the
old record: fresh chain after cancelled work
(`scan_console/tests.rs:1194-1239`, asserts `Cancelled` kept plus new
`Queued` with `attempt=0` and a different chain) and fresh chain after
exhaustion (`scan_console/tests.rs:1825-1843`, asserts the attempt-4
`Failed` kept plus a new `Queued` chain). The installed repair replay
records the same shape with distinct native job/retry-chain IDs for D2
and D3
(`docs/review/phase-2-integration/installed-journey/run-20260909.md:88-99,130-133`).

### 3. Disable/remove and status-refresh races remain safe

- Disable rejects at the durable boundary: `enqueue_scan_tx` returns
  `Conflict` for a disabled root (`execution.rs:731-734`), and
  `retry_failed_scan_job` returns `false` for a disabled root
  (`execution.rs:1401-1404`), which the native layer reports as
  `conflict`. The disabled-race native test proves both commands fail
  closed while the failed job stays at attempt 1
  (`scan_console/tests.rs:1104-1145`).
- Disable/remove invalidate atomically with the configuration change in
  the same transaction (`cancel_root_work`, `execution.rs:819-836`), so
  a mid-queue/mid-run disable or remove cannot publish stale rows; a
  re-added path mints a fresh root id.
- The renderer refreshes after both success and failure
  (`apps/client/src/library/LibraryPage.tsx:472-483,506-531`) under
  `actionSequence` guards, so a stale render (enabled at render,
  disabled at action) resolves to the `conflict` message plus a fresh
  status rather than a stuck Retry. The exact interleave
  (enabled-status observed, disable lands, then action) is
  reviewed-by-code against the fencing above; no altered-semantics
  timing test was added to chase it.

### 4. Native and review-harness rendering are accurately distinguished

The context is explicit at every layer: `LibraryRenderContext`
(`apps/client/src/library/contracts.ts:23`) defaults to `"native"`;
the product entry selects native
(`apps/client/src/entries/desktop.tsx:18`) while the capture harness
opts into `"review-harness"`
(`docs/review/phase-2-library/capture.mjs:115-117`);
`LibraryPage` gates both `data-review-adapter` and the harness badge on
the context (`LibraryPage.tsx:659-682`), and the empty-state copy no
longer mentions harness controls. The client test renders both
contexts and asserts the badge/attribute appear only in the harness.
The installed D1 replay reports `data-review-adapter="native"` with no
visible badge
(`installed-journey/run-20260909.md:53-62`).

### 5. #97's barriers and fake clocks prove the claims

- `claim_due`/`execute_pending` are the production poll-loop body split
  for interleaving (`scan_console_host.rs:474-568`), not mocks: the
  convergence test holds a scan durably running, retriggers
  (`already_running`), executes with the unchanged tree, then ticks the
  follow-up with the later tree. It asserts durable states
  (`Interrupted`, exactly 3 jobs, one `Queued` follow-up), the
  no-publication intermediate (Library still 1 present row, follow-up
  `queued` with null `runId`), and the authoritative convergence
  (`a.flp` retained as `missing`, `b.flp` `present`). That is a
  ledger-and-publication proof, not a mirror of the test's own logic.
- The idle-burst test drives the production `Coalescer` plus the real
  supervisor `poll` against the durable ledger: 5,000 + 5,000 signals
  across two windows stay at exactly 1 queued job. The running-burst
  flag path was already covered; this pins the idle queued-slot path.
- The stale-generation test drives real `set_scan_root_enabled_at` /
  `remove_scan_root_at` / `add_scan_root` transitions with per-step
  `jobs_for` counts: 0 jobs while disabled, 1 fresh gap after
  re-enable with stale replay still 1, replacement 1 + old 1 with
  retired-generation replay still 1.
- Honest boundary: the filesystem port is scripted in-memory per the
  repo's scanner test rules, and installed timing (queued visibility,
  burst coalescing, coverage-loss timing) remains an installed-only
  gap. No production delay was added to make transients visible.
